Qwen3-4B + GRPO + LoRA under an 8 GB GPU cap — DON'T SHIP

Every number below comes from a saved log in results/ and is reproduced by uv run python scripts/final_analysis.py (verification script). Rules and predictions were committed to git before each run (predictions/PREDICTIONS.md, commit times are the proof); the experiment log keeps every failure unedited (results/RESULTS_LOG.md, entries E00–E20).

1. Verdict

GRPO training on 5-number Countdown puzzles did beat the base model on 500 held-out puzzles (+5.6 points). But the shuffled-reward control, trained with no real signal, gained more (+9.6). So the gain cannot be credited to the reward. Both gains come mostly from answers that finish within the 512-token cap rather than better arithmetic: among finished answers, accuracy fell. Two of the pre-registered SHIP conditions fail (H26 control, H9a skill vs format), so the verdict is DON'T SHIP. The system itself (own layer-to-layer engine, 8 GB cap, exact resume, two independent checkers) works and is verified.

What must change before this could ship: (1) remove the length confound: re-pilot with a cap or prompt where < 5% of base answers are cut off (my own rule 6; I relaxed it to 512 tokens for the free-GPU budget, and that is what the verdict turned on); (2) ≥ 3 seeds per arm, decided on the mean (one control seed can drift lucky); (3) ship the adapter or an fp32 merge: the bf16 merge lost 87% of the change (H29).

2. Setup

Task. Countdown: use every given number once with + − × ÷ to hit a target. Puzzles are generated with a known solution (all 10,500 reference solutions score 1.0), train/held-out/pilot splits share no puzzle (hash check). Reward 1/0 from an AST-whitelisted exact-fraction checker (last <answer> block; cheat tests for extra/repeated numbers, unary minus, floats, **, //, ×1 tricks). Pilot path (rule written before each pilot): n4 with prompt v1 13.2% → prompt v2 (no example to copy, brief working) 31.2% but 65% cut off at 256 tokens → pilot 2 at 512 tokens: n4 56.2%, n5 21.5% (mixed groups 47%) → n5 chosen, confirmed 23.5% over 200 prompts. Training: G = 8, 6 prompts/step (48 rollouts), 40 steps, T = 1.0, LoRA r16 α32 on 7 projections (33.0 M params), AdamW lr 2e-5, 2 warm-up steps, β = 0 (KL to base logged), std-scaled advantages, constant loss normaliser. Control = identical run, same seed and prompt order, rewards shuffled.

Hardware deviation. The only GPU available was a free Kaggle T4 (Turing, 16 GB, no bf16, no SSH, ~12 h sessions, ~30 GPU-h/week). Handled as follows; total use ≈ 18 GPU-h.

3. Engineering

Own L2L engine (src/soupgrpo/l2l.py): weights live in pinned host memory, one flat buffer per layer; a ring of 3 GPU buffers is filled by a copy stream with CUDA events (prefetch); one engine does prefill, KV-cached decoding and training; training saves each layer's input to host and recomputes in backward; log-probs in 512-row chunks. Equivalence: vs HF Qwen3 on CPU, fp32 logits 1.1e-6 and all LoRA grads ≤ 2.1e-6, bf16 within the measured noise floor, greedy 50/50 identical (H17, H18); on CUDA with prefetch (2 and 3 buffers, checksums on) identical to the CPU engine (E02b).

The finding: under the cap, the drafter's ~1.5 GB halves the rollout batch, and plain L2L decoding is copy-bound, so its throughput grows almost linearly with batch. DFlash at 24 rows equals plain at 48 (passes fell 3.2×, but each 16-token verify pass costs 0.80 s instead of 0.60 s). DFlash pays only at small batch. Greedy identity (H21) on base: 82/96 answers identical, every divergence at an fp16 near-tie (top-2 gap ≤ 0.031; the 90% target missed). Sampling is unbiased (H22: all 15 chi-square p > 0.05/15, min 0.24; the deliberately biased rule is caught, p ≈ 0). The training-phase prefetch result suggests that phase is host-bound (not profiled). The trained adapters were not attached to that run, so H7, and H21/H22 with the adapter, are still open.

4. Did the model learn? (proof and its limits)

  • Signal reached the adapter: adapter norm 0 → 0.76; exact KL(adapter‖base) on its own held-out answers 0.065/token for main vs 0.029 for control (H28 ✓).
  • But not more correct answers than no signal: main − control −4.0 [−8.4, +0.4] (H26 ✗). Training curves do not prove learning here: with identical prompt order, training reward rose the same in both arms (main +0.18, control +0.22 over 40 steps). I first read the main curve as learning (E16) and corrected it after the control (E17).
  • Format vs skill: the value-correct rate rises with the reward, and the tag rate rises the same (+8.4): the extra correct answers are the extra finished ones (H9a ✗).
  • Checker is right: an independent re-implementation (string search + hand-written parser, no shared code) agrees on 100% of 3,600 saved answers; on the pre-fix pilot files it flags exactly the 52 answers the E11 fix changed there. Hand audit of 30 trained answers: 30/30 correctly scored, including one cheat attempt (80/11)*(11/80) (rejected).
  • Other skills: GSM8K −2 points, not significant (H10 ✓).
  • Not detected by this setup: overfitting to the puzzle generator's style (train and test share it); effects that need > 40 steps; seed-to-seed variance (one seed per arm).

6. Hypotheses: prediction vs result

✓ confirmed: H1, H4 (36 copies per pass, independent of batch), H8, H10, H15, H17, H18, H19, H20, H24 (n5 23.5%), H25 (mean 46% zero-advantage groups, single steps up to 100%), H28, H30, H33, H2, H5, D0, H23 (B 8–32), H22 (base). ✗ rejected: H26, H9(a) (the verdict), H12, H13, H14, H27 (bf16), H29 (predicted < 30% of ΔW lost, measured 87%: I estimated ΔW at 1e-4–4e-4, real ΔW was mostly below half a bf16 step ≈ 6e-5), H31 truncation part, H32 n4 part (56.2 vs ≤ 55), H3 (decode compute is ~5.5 ms/layer, not 1–2; training copies are off the critical path), H6 (DFlash 0.98× on a real step). Open: H7, H21/H22 with the adapter, H23 at batch 48 (follow-up notebook ready); H16 (estimated 3–5% from copy counts, not profiled).

7. What surprised me, what still concerns me

The control result surprised me most: a run with shuffled rewards beat the real run. My best reading is that 79% of base answers were cut off, so almost any change in verbosity moves the score, and the metric rewarded finishing more than reasoning. I set the < 5% truncation rule myself and then relaxed it for the GPU budget; the verdict turned on exactly that relaxation. It still concerns me that I cannot separate "control drifted lucky" from "the process itself shortens answers" with one seed per arm, and that the bf16 merge, the normal way to ship, silently produced a different model.

8. AI tool use

The plan, code, notebooks and analysis were written with an AI coding assistant (Claude Code); I ran every GPU notebook, read the outputs and made the calls on what to run next. What was verified rather than trusted: the engine against Hugging Face's reference (fp32 1e-6), every checker change against hand-read answers and a second independent checker, every memory and time claim against raw nvidia-smi and host logs. What was changed or redone after checking: the checker (E11), the cap formula (E12), the host-memory buffer and the trivially-passing mechanics tests (E14), and the assistant's own reading of the training curve as learning, which the control disproved (E16 → E17).

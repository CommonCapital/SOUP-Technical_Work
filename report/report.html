Qwen3-4B + GRPO + LoRA under an 8 GB GPU cap — DON'T SHIP

All numbers here come from saved logs in results/. You can reproduce them with uv run python scripts/final_analysis.py. I wrote my predictions and decision rules into predictions/PREDICTIONS.md and committed them before each run, so the git timestamps show I did not change them afterwards. Every failure is kept as it happened in results/RESULTS_LOG.md (entries E00–E20).

1. Verdict

The trained model is better than the base model on 500 new puzzles: +5.6 points. But my control run, trained with shuffled rewards (so no real learning signal), got +9.6, even more. So I cannot say the reward caused the gain. When I looked closer, most of the gain in both runs comes from answers that now finish inside the 512-token limit, not from better arithmetic. Among answers that do finish, accuracy actually went down. Two of my own SHIP conditions fail (H26: beat the control; H9a: skill, not format), so the answer is DON'T SHIP. The system around the model (my own layer-by-layer engine, the 8 GB cap, exact resume, two independent checkers) works, and I verified it.

What I would change before this could ship: (1) Fix the length problem first. Pick a token limit or prompt where fewer than 5% of base answers get cut off. That was my own rule; I relaxed it to 512 tokens to fit the free GPU budget, and the verdict turned on exactly that. (2) Run at least 3 seeds per arm and decide on the mean, because one control seed can just get lucky. (3) Ship the adapter, or merge in fp32. The bf16 merge lost 87% of the change (H29).

2. Setup

Task. Countdown: use every given number once with + − × ÷ to reach the target. I generate each puzzle from a known solution, so all of them are solvable (all 10,500 reference solutions score 1.0). Train, held-out and pilot sets share no puzzle (checked by hash). Reward is 1 or 0 from a checker that only accepts a whitelist of Python syntax and computes with exact fractions. It reads the last <answer> block and has tests for cheats (extra or repeated numbers, unary minus, floats, **, //, ×1 tricks). How I picked the difficulty (rule written before each pilot): 4 numbers with prompt v1 gave 13.2%. Prompt v2 (no example to copy, brief working) gave 31.2%, but 65% of answers were cut off at 256 tokens. At 512 tokens: 4 numbers 56.2%, 5 numbers 21.5%, with 47% mixed groups. I chose 5 numbers, and it held at 23.5% over 200 prompts. Training: 8 answers per prompt, 6 prompts per step (48 rollouts), 40 steps, temperature 1.0, LoRA rank 16, α 32 on 7 projections (33.0 M parameters), AdamW lr 2e-5, 2 warm-up steps, no KL penalty (KL to base is only logged), std-scaled advantages, constant loss normaliser. The control is the same run with the same seed and prompt order, but with shuffled rewards.

Hardware change. The only GPU I had was a free Kaggle T4: Turing, 16 GB, no bf16, no SSH, sessions of about 12 h, about 30 GPU-hours a week. This is how I handled it. In total I used about 21 GPU-hours.

3. Engineering

My own L2L engine (src/soupgrpo/l2l.py). The weights stay in pinned CPU memory, one flat buffer per layer. A ring of 3 GPU buffers is filled on a separate copy stream with CUDA events, so the next layer loads while the current one computes (prefetch). The same engine does prefill, KV-cached decoding and training. In training it saves each layer's input to CPU memory and recomputes the layer in the backward pass. Log-probs are computed in chunks of 512 rows. Is it correct? Against Hugging Face's Qwen3 on CPU: fp32 logits differ by 1.1e-6 and all LoRA gradients by ≤ 2.1e-6, bf16 is within the measured noise, and greedy output is identical on 50/50 prompts (H17, H18). On CUDA with prefetch (2 and 3 buffers, checksums on) it matches the CPU engine exactly (E02b).

The main lesson: under the cap, the drafter's ~1.5 GB halves the rollout batch. Plain L2L decoding is limited by copying layers in, so it gets almost linearly faster with a bigger batch. DFlash at 24 rows ends up equal to plain at 48: it needs 3.2× fewer passes, but each 16-token verify pass costs 0.80 s instead of 0.60 s. So DFlash only pays at small batch sizes. Greedy identity on the base model (H21): 82/96 answers identical, and every difference starts at an fp16 near-tie (top-2 gap ≤ 0.031), but that misses my 90% target. Sampling stays unbiased (H22: all 15 chi-square p > 0.05/15, lowest 0.24, and the test does catch a deliberately biased rule, p ≈ 0). The prefetch result in training suggests that phase is limited by CPU-side work, but I have not profiled it. The trained adapters were not attached to that session, so H7, and H21/H22 with the adapter, are still open.

4. Did the model learn? (proof and its limits)

  • The signal reached the adapter: adapter norm 0 → 0.76. Exact KL(adapter‖base) on its own held-out answers is 0.065 per token for main vs 0.029 for control (H28 ✓).
  • But it did not get more answers right than training with no signal: main − control −4.0 [−8.4, +0.4] (H26 ✗). The training curves don't prove learning here either: with the same prompt order, the training reward rose by the same amount in both runs (main +0.18, control +0.22 over 40 steps). At first I read the main curve as learning (E16). The control showed I was wrong (E17).
  • Format vs skill: the share of correct values rises with the reward, and the share of proper tags rises the same (+8.4). The extra correct answers are just the extra finished ones (H9a ✗).
  • The checker is right: a second, independent checker (string search plus a hand-written parser, no shared code) agrees on 100% of 3,600 saved answers. On the old pilot files it flags exactly the 52 answers that the E11 fix changed. I also checked 30 trained answers by hand: all 30 scored correctly, including one cheat attempt (80/11)*(11/80) (rejected).
  • Other skills: GSM8K −2 points, not significant (H10 ✓).
  • What this setup cannot see: overfitting to the style of my puzzle generator (train and test share it), effects that need more than 40 steps, and seed-to-seed variance (one seed per arm).

6. Hypotheses: prediction vs result

✓ confirmed: H1, H4 (36 copies per pass, same for any batch), H8, H10, H15, H17, H18, H19, H20, H24 (n5 23.5%), H25 (on average 46% of groups had zero advantage; single steps up to 100%), H28, H30, H33, H2, H5, D0, H23 (batch 8–32), H22 (base). ✗ rejected: H26, H9(a) (the verdict), H12, H13, H14, H27 (bf16), H29 (I predicted < 30% of ΔW lost and measured 87%: I estimated ΔW at 1e-4–4e-4, but most of the real ΔW was below half a bf16 step, ≈ 6e-5), the truncation part of H31, the n4 part of H32 (56.2 vs ≤ 55), H3 (decode compute is about 5.5 ms per layer, not 1–2; in training the copies are not on the critical path), H6 (DFlash 0.98× on a real step). Still open: H7, H21/H22 with the adapter, H23 at batch 48 (follow-up notebook is ready), H16 (estimated at 3–5% from copy counts, not profiled).

7. What surprised me, what still worries me

The control surprised me most. A run with shuffled rewards beat the real run. My best explanation is that 79% of base answers were cut off, so almost any change in how long the model talks moves the score, and the metric rewarded finishing more than reasoning. I set the < 5% truncation rule myself and then relaxed it to fit the GPU budget, and the verdict turned on exactly that. What still worries me: with one seed per arm, I can't tell "the control got lucky" apart from "this training process itself makes answers shorter". And the bf16 merge, the normal way to ship, quietly produced a different model.

I used an AI coding assistant (Claude Code) to write most of the code and notebooks, to help with the analysis, and to draft this report. I ran every GPU notebook myself, read the outputs and decided what to run next. I did not take its output on trust. I checked the engine against Hugging Face's reference (fp32, 1e-6), every checker change against answers I read by hand and against a second independent checker, and every memory and time claim against raw nvidia-smi and host logs. Things I changed or redid after checking: the checker (E11), the cap formula (E12), the host-memory buffer and the mechanics tests that passed for a trivial reason (E14), and the assistant's own reading of the training curve as learning, which the control disproved (E16 → E17).
